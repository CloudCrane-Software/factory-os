## 一、运营者操作三步

### 第 1 步：备卡面 —— Issue 必须自包含

沙箱 agent **读不到厂内任何档案**（也无权访问厂内网络），卡面必须能单独回答「做什么 / 能改什么 / 不能改什么 / 怎么验收 / 证据落哪 / 不做什么」六问。六要件缺一即回炉补卡，不许带病发车。

| # | 要件 | 要点 |
|---|---|---|
| 1 | 标题 + 卡号 / 债号 | 分支 slug 的来源；占用闸与台账回写的键 |
| 2 | 背景与**已核实**前提 | 写「你要施工而不是重新调查」；既有结论带 `file:line` 出处 |
| 3 | **显式「不许假设的前提」** | G1 范式：把最容易想错的地方写成禁令（例：GitHub 侧仓定位、默认分支名、判据面只许变严） |
| 4 | 要做的几件 + 逐件完成定义 | 编号；每件一条可判定的完成定义（不是「优化一下」这种） |
| 5 | `allowed_paths` + **禁改面逐一点名** | 只许改 / 新增的路径白名单；判官面 / 门禁件 / 判据件逐文件点名，**不写泛指** |
| 6 | 验收命令集 + 期望退出码 + 证据落盘位置 + 「本卡不做什么」 | 边界节是交付物的一部分，不是客套 |

**派前三闸（建 Issue 之前，运营者做）：**

1. **占用机检**：`python3 -I tools/dispatch-occupancy-check.py <债号>`（台账面 / 登记面 / 在飞面三面机检；任一面占用或不可解析 ⇒ fail-closed 拒派）。被拒 ⇒ 换锚债或先登记债行；**禁 `--force-occupancy`**（`bot-bridge.py` 的逃生口在本环禁用——P5 首环零豁免，占用即占用，幂等覆盖不构成豁免）。
2. **脱敏闸**：卡面文本落成文件后过 bot-scrub 规则族（`python3 -I 30-工件/外派-bot-试点/tool/bot-scrub.py <卡面所在目录> --out <verdict.json>`；退出码 0 = 零命中可发，1 = 命中或覆盖不全拒发，2 = 结构失败拒发）。Issue 建在**公开仓**，全网可读 ⇒ 零命中才建。
3. **自包含六要件核**：见上表；缺一项回炉。

### 第 2 步：填五个占位符 → 整段复制

| 占位符 | 填什么 | 注意 |
|---|---|---|
| `<ISSUE_URL>` | 刚建的 Issue 完整 URL | 与分支名里的 issue 号一致 |
| `<ISSUE_BODY>` | Issue 正文**全文**（自包含卡面） | 整段替换，**不许只贴链接**——沙箱读不到厂内档案 |
| `<APP_TOKEN 获取方式>` | 本环 installation token 的获取 / 注入方式 | 见下 |
| `<分支名 task/issue-slug>` | 实际分支名，形如 `task/42-bak-cleanup` | 与 PR `head` 逐字一致；slug 用卡面定的 |
| `<BEACON_SNIPPET>` | 观测信标发射器内联片段（§8.3 用；stdlib python + `$AF_OTLP_INGEST_TOKEN` 注入；token 值禁入 Issue/仓/转录） | 本卡不启用 L3 时填 `L3-off` |

**`<APP_TOKEN 获取方式>` 的标准填法**（运营者本机现取、一次性注入沙箱会话；App 私钥只经「openBao → JWT 铸造」管线，不落地、不进文档、不打印）：

- 读字段名 / 长度：`bao-agent get company/Git-Platform/Github/CloudCrane-Software-Repo-Writer-APP`
- 取私钥到 `mktemp` 0600、用后 `shred -u`：`bao-field company/Git-Platform/Github/CloudCrane-Software-Repo-Writer-APP private_key > "$(mktemp -p /tmp k.XXXX)" && chmod 600 "$KF"`
- 签 RS256 JWT（`iat` = now−60、`exp` = now+600、`iss` = app_id）→ `POST /app/installations/<INSTALLATION_ID>/access_tokens` → 得 `ghs_...`（寿命 1 小时）
- 把 token 作为**会话首条消息里的一个环境变量**注入沙箱（变量名纪律同 3.4：以 AF_GH 开头；token 本体只经会话注入，形态示例禁入公开仓——bot-scrub G-13 fail-closed），并明示三条：1 小时失效、仅限本次会话、用完作废
- 兜底（不推荐长期用）：fine-grained PAT（仅选定仓 Contents RW + PRs RW + Issues RW，90 天）——无安装级吊销面，只作首环应急，用后即废

**复制纪律（三条都是硬要求）：**

- **整段复制**：第二节模板从「你是 af……」到「诚实性高于完成度……」一整段。**禁只粘任务书不粘禁项**——红队双案的直接温床就是「任务书到位、禁项被稀释」。
- 禁删改第 0 节（禁项）与第 6 节（交卷自检清单）；禁在复制件里夹带 token 之外的任何凭据。
- 发车前五个占位符必须已填实（不留 `<...>` 字样）——沙箱不该再问你要资料。

### 第 3 步：粘进沙箱会话并发车

- **一次卡一个会话**，不要多卡混在一个会话里（归因与占用会串）。
- 粘贴整段 → 发车。此后运营者只做三件事：异常裁决、红件收卷复核、首环读数回填。
- **发车前前置确认**（P5 的前提，缺一项即降级，不许硬发车）：
  1. P2 出口已过——anolis self-hosted runner 在线、label `anolis-heavy`、容器作业隔离在位；否则 runner 宿主不直跑 untrusted PR 码，全门跑不起来；
  2. af 仓分支保护在位——要求 PR + required check `gates` + 不 bypass + **仓级 CODEOWNERS 判官保护**；
  3. 卡面债号在台账有行——否则占用闸 fail-closed BLOCK，派不出去。

## 三、运营者收卷复核与首环读数

沙箱自报**不作证据**（外派纪律：一切门读数以环上重跑为准）。运营者收卷时按下表复核，红一件即走异常队列：

| 复核项 | 判据 |
|---|---|
| PR 已关联 Issue | 正文有 `Closes #<issue 号>` |
| 归因在位 | commit trailer + PR 正文均有 `Co-Authored-By`；PR 作者 = App bot |
| 禁改面零改动 | `git diff --name-only <base>...<head>` 与判官面清单求交为空（CODEOWNERS 侧同步验证：改了根本合不进去） |
| 路径外零改动 | 同上，与卡面 `allowed_paths` 求交全覆盖 |
| 验收命令与退出码 | PR 正文 ④ 段逐条有「命令 + 退出码」 |
| 证据在盘 | PR 内 `poc/<slug>/` 读数文件可点开、与正文点名一致 |
| gates 全绿 | Actions `gates` 全绿（环腿读数，不采信沙箱自报） |
| 零凭据 | diff / 证据 / PR 正文无凭据形态 |

**首环读数（P5 出口，回填 `03-主会话交接.md` §六判定表与变更日志）**：PR 号 + `gates` 各 job 结论 + 自动合并是否发生 + Issue 是否关 + manifest commit sha + 异常队列是否有本卡记录。

**首卡建议**（`03-主会话交接.md` §三.3）：`tools/` 210 个 `.bak` 清理——确定性验收（清理前后件数对账 + 门不劣化）、低风险真代码环。注意该卡落在 `CloudCrane-Software/factory-os`：把第二节模板里的仓名一行替换为 `factory-os`，其余纪律原样适用（`gates` required check 同样要在该仓分支保护里勾上）。

## 四、边界与后续接缝

**本模板不作**：不作规划环（Issue 由规划环 / 主会话产出，P4 才定时化）；不作工厂侧自动派发（后续项）；不作自动合并 / 关 Issue / manifest commit 的实现（环腿，沙箱与运营者都不碰）；不作沙箱选型、计费与隔离规格（沙箱自带电脑，本模板只约束它与 GitHub 的交互面）。

**后续自动派发的接缝**（机械化时按此替换人工三步）：第 1 步「建 Issue」= 规划环产出；第 2 步「填占位符 + 整段复制」= 派发器渲染同一模板（占位符改由机器填）；第 3 步「粘进沙箱会话」= 沙箱 API / 门户投递（占用闸与脱敏闸前置不变，`--force-occupancy` 依旧禁用）。**第二节模板正文在手动与自动两种模式下应保持逐字一致——它是沙箱 agent 的唯一契约面。**
